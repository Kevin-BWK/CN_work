## 1. 定位与架构结论

本项目是课程选题 2 的 Windows 本机网络流量分析桌面程序。用户选择一张网卡，采集可见报文，查看链路层、网络层和传输层关键字段，统计 IP 长度和协议分类，并保存、重新读取抓包文件。

系统采用单进程、多线程结构：Npcap 提供抓包能力，Scapy 负责报文解码和文件格式，项目代码负责字段提取、统计口径、会话调度和可视化。不存在服务端、数据库、云端上传或分布式采集。

当前主流程可演示，正常 Ethernet II 报文及小文件回读已有验证。架构方向继续沿用；2026-11-16 已补齐解析异常隔离、记录失败降级、磁盘余量保护和界面后台任务，连续一天以上的验收仍在进行。

### 1.1 支持范围

- 每个实时会话选择一个接口；GUI 开始新会话时创建新的 `CaptureSession`。
- 面向 Ethernet II、单层 VLAN、普通 IPv4/IPv6、TCP/UDP 字段；非首片不推测端口。
- ARP 等数据可计入“其它”，不提供完整应用层协议分析、TCP 流重组或载荷解密。
- 以 Npcap 暴露的链路数据为准，无线网卡通常以 Ethernet 形式交付报文；本软件不提供无线监听模式管理。
- 接口枚举包含回环、虚拟网卡等，但当前解析器和记录器没有保留链路类型，不代表这些接口均被正确支持。
- BPF 是抓包前过滤，不是对已抓报文的显示筛选；统计和保存均只针对过滤后的输入。
- SYN 泛洪、ICMP 异常检测属于可选扩展，当前未实现。

## 4. 线程、数据流与容量

### 4.1 实时抓包路径

```mermaid
flowchart LR
    NIC[网卡 / Npcap] --> Sniffer[Scapy 抓包线程]
    Sniffer --> Q1[抓包队列 50000 条]
    Q1 --> Process[会话处理线程]
    Process --> Parse[解析 PacketRecord]
    Parse --> State[累计统计和最近记录]
    State --> Snapshot[SessionSnapshot]
    Snapshot --> GUI[Qt 主线程 250ms 轮询]
    Process --> Q2[记录队列 10000 条]
    Q2 --> Writer[记录线程]
    Writer --> PCAP[pcapng 分段]
    Snapshot --> Monitor[资源线程 10s 采样]
    Monitor --> CSV[resources.csv]
```

1. `AsyncSniffer(store=False)` 调用抓包回调。Scapy 已提供报文对象，回调将其序列化为字节，保存时间戳和线上长度，形成 `RawPacket`。
2. 回调非阻塞入队；队列满时丢弃该条，增加应用采集队列丢弃计数。
3. 处理线程重新以 `Ether(raw)` 解码，调用 `parse_packet()`，得到 `PacketRecord`。
4. 处理线程在锁内更新聚合统计和最近记录，然后将原始报文送入记录队列。记录队列满时增加 `record_dropped`，统计已更新但该条不会落盘。
5. 记录线程写入 pcapng；GUI 每 250ms 获取统计及最近记录快照，更新表格、详情与图表。
6. 资源线程每 10 秒采样并写 CSV。GUI 的 CPU/RSS 显示由界面另外调用 psutil 获取，不由日志线程推送。

### 4.2 状态所有权与内存

| 状态 | 所有者/同步方式 | 容量和限制 |
| --- | --- | --- |
| 抓包队列 | `CaptureWorker` 的线程安全队列 | 50000 条原始报文 |
| 记录队列 | `CaptureSession` 的线程安全队列 | 10000 条原始报文 |
| 累计计数 | 处理线程更新；快照读取使用 `RLock` | 不保存全部历史报文对象 |
| 最近报文 | `deque(maxlen=10000)`，与统计共用锁 | 实时表格只能查看最近 10000 条 |
| 离线报文 | `analyze_pcapng()` 的局部缓存 | GUI 请求最近 50000 条；统计仍扫描整个文件 |
| 统计/会话快照 | 冻结 dataclass 和 tuple | 传递字段及计数，不传递全部原始字节 |
| pcapng 文件 | 单个记录线程写入 | 分段数量和总磁盘占用目前没有上限 |

队列限制的是条数，不是字节数；大报文和队列积压仍可能占用大量内存。正常流量下使用固定缓存有助于控制增长，但不能替代实测，也不能承诺 24 小时必然低于某个内存值。

统计快照和最近列表复制会占用锁；GUI 表格在缓存首条发生变化时重置模型。两个柱状图每次刷新会清除并重建图元，即使当前标签页不可见也会更新。因此仍需在长时间、满缓存情况下测量刷新成本。

## 5. 协议模型与统计口径

### 5.1 数据契约

- `RawPacket(timestamp, data, wire_length)`：保留原始报文、时间戳和捕获来源提供的线上长度；当前缺少链路类型。
- `PacketRecord`：序号、时间、帧长度、MAC、EtherType、VLAN ID、IP 字段、端口、TCP 标志、摘要及解析错误。字段缺失时通常用 `None` 表示。
- `StatsSnapshot`：报文总数、解析成功/错误数、IPv4/IPv6/其它数量、捕获字节数、长度频次、分桶和协议计数，以及速率。
- `SessionSnapshot`：统计快照、最近记录、运行标记、开始时间、运行时长、队列深度、应用丢弃计数、记录状态、分段列表和最近错误。

### 5.2 字段解释

| 字段 | 当前实现 | 需要注意的边界 |
| --- | --- | --- |
| MAC、EtherType | Ethernet 字段；VLAN 时取内层类型 | 外层 EtherType 未单独保留；802.3/LLC 帧已能安全记录（标记“不支持类型”，不再抛异常），但没有网络层字段 |
| VLAN | 遍历 `Dot1Q`，每次覆盖 VLAN ID | 多标签时只保留最后一层 ID，不是完整标签栈 |
| IP 地址、版本 | IPv4/IPv6 层字段 | 当前按 EtherType 选择对应解析分支 |
| TTL/Hop Limit | IPv4 TTL；IPv6 Hop Limit | GUI 对 IPv6 使用 Hop Limit 名称 |
| 协议号 | IPv4 `proto`；IPv6 有 TCP/UDP 时取最终协议 6/17，否则取基础头 Next Header | 有扩展头且非 TCP/UDP 时（如 HBH+ICMPv6）可能显示基础头值，属于已定义口径 |
| TCP/UDP 端口 | 只看最外层 IP 头直接承载的传输层 | 隧道报文不再混用外层 IP 与内层端口；非首片不取端口 |
| TCP 标志 | SYN、ACK、FIN、RST 位 | 不表示已完成 TCP 连接跟踪或状态机分析 |
| 分片 | IPv4 非首片、IPv6 非首片不提取端口 | 不做分片重组 |
| 线上长度 | `RawPacket.wire_length` 透传给解析器 | 截断帧的详情显示真实线上长度；回读文件时取记录中的 wirelen |

### 5.3 长度与分类

本项目已采用以下口径，原课程要求的区间写法存在歧义，最终报告需注明项目解释：

- IPv4 长度取 IP 首部的总长度；IPv6 通常取 `40 + Payload Length`，代码在该字段为 0 时退回序列化长度。
- 长度折线图和分桶只统计有正 IP 长度的记录；ARP 等非 IP 数据不进入长度统计。
- 三个分桶互斥：`<=46`、`47–1499`、`>=1500`。
- IPv4/IPv6/其它按解析结果的 `ip_version` 分类；解析失败可能归入“其它”，与纯 EtherType 分类并不完全等价。
- 累计字节统计的是捕获帧字节数，不是 IP 字节数，也不是完整线上占用。
- 速率是最近 5 个整秒桶内的报文数除以 5，不是链路带宽或吞吐量。

长度图补齐未出现长度的零计数，再绘制曲线；这避免把未观测区间直接连成斜线。默认查看 0～1600 字节，完整视图的绘制数组当前截到 65535，超长 IPv6 情形尚未完整处理。

### 5.4 计数一致性

正常无丢弃、正常停止并排空队列时，应满足：

```text
总记录数 = 解析成功数 + 解析错误数
总记录数 = IPv4 数 + IPv6 数 + 其它数
三段长度计数之和 = 有效 IP 长度计数之和
实时累计数量和分布 = 回读保存文件后的累计数量和分布
```

最后一条比较累计数量和分布，不比较以当前时间为基准的实时速率；它还有前提：当前统计先于记录，记录队列丢弃或写入失败时，文件数量可能小于实时统计。资源 CSV 的 `captured` 实际取处理后的统计总数，不是 Npcap 原始接收数。现有“丢包”指标只有应用队列丢弃，不包括驱动丢包，界面上的 0 不能解释为整条链路零丢包。

## 6. 文件、回放与部署

### 6.1 保存格式

GUI 默认在 `data/sessions/年月日_时分秒/` 下建立会话目录：

| 文件 | 内容 | 当前行为 |
| --- | --- | --- |
| `capture_时间_序号.pcapng` | 原始字节、时间戳、捕获长度和线上长度 | 记录器写死 Ethernet linktype=1 |
| `session.json` | 开始/结束时间、接口、BPF、版本、分段名 | 正常停止流程写入；直接写文件，不是原子替换 |
| `resources.csv` | 资源采样和应用计数 | 每 10 秒写入并 flush，停止时补一条 |

分段阈值为 `256 * 1024 * 1024` 字节，即 256 MiB；按“原始字节数 + 每包估算 64 字节开销”累计，不保证每个文件精确等于阈值。分段控制单文件大小，不控制总磁盘用量，也没有自动淘汰旧文件。

导出单文件时，一个分段直接复制；多个分段流式读取后重新写入临时 pcapng，再替换目标文件。不要把这描述为所有写入均具备原子性。长稳脚本结束时会额外导出完整文件，需要考虑近一份原始记录大小的额外磁盘空间。

### 6.2 离线回读

`read_capture()` 选择 Scapy 文件读取器，逐条产生 `RawPacket`；`analyze_pcapng()` 复用实时解析器和统计器。这个共享路径减少实时与离线统计规则不一致的风险。

目前 GUI 在主线程同步调用分析函数及导出函数，没有进度或取消。流式读取只避免一次性载入全部原始报文，并不等于后台读取。打开文件会先停止实时抓包；成功后进入离线展示，运行时长栏显示文件首尾报文时间差，不是原会话的连续运行证明。

### 6.3 部署与入口

- `run.bat` / `run_console.bat`：使用本地 `.venv`，要求先安装项目及依赖。
- `build.bat`：PyInstaller one-dir 打包；`run_exe.bat` 启动打包程序。
- 发布时需携带整个 `dist/NetworkTrafficAnalyzer/`，不能只复制其中的 `.exe`。
- Npcap 驱动不是 Python 依赖，另一台电脑需要单独准备。
- 项目当前脚本部分使用固定 `E:\CN_work`、`WLAN` 或历史测试 IP；还没有完整的新电脑初始化流程。
- `.venv`、`data`、`dist`、`build` 等被 Git 忽略；从仓库克隆不会自动得到可执行程序和测试抓包证据。

## 7. 会话生命周期与故障边界

当前生命周期由多个布尔标记、线程引用和 `None` 队列哨兵实现，没有统一状态机。

| 阶段 | 当前实现 | 限制 |
| --- | --- | --- |
| 开始 | 建立记录器和日志线程、处理线程，然后启动异步抓包 | 抓包启动仍用 150ms 后检查，未改为可靠就绪事件 |
| 运行 | 处理报文、统计、入记录队列，GUI 轮询快照 | 处理线程异常会置 `running=False` 并显示错误；记录线程失败或磁盘不足会停止记录、继续统计 |
| 停止 | 先停抓包，再用带 5s 超时的哨兵入队、join 15s、关闭记录器、写元数据 | 线程未在时限内停止时保留文件不关闭，并记录错误 |
| 退出 | 窗口关闭时同步调用停止 | 故障路径最坏约 35s，仍会短暂阻塞界面 |

2026-11-16 复现并修复了两条关键故障路径：

1. 合法 `Dot3/LLC/STP` 帧经 `Ether(raw)` 得到 `Dot3` 对象，访问不存在的 `type` 抛出异常；处理线程退出而会话仍报告运行。现在解析器把 802.3/LLC 记为“不支持类型”，处理循环另有兜底捕获，线程不再退出（测试 `test_8023_stp_frame_is_recorded_as_unsupported`）。
2. 记录器抛错后记录线程退出但 `_recording=True`；记录队列满时关闭逻辑阻塞在无超时哨兵入队。现在记录失败会置 `_record_failed`、停止记录并关闭文件，哨兵与 join 全部带超时（测试 `test_stop_is_bounded_when_recorder_failed_and_queue_full`）。

磁盘余量低于 2 GiB 时记录器抛 `LowDiskSpaceError`，会话停止记录、继续统计并在状态栏提示；导出前也检查所需空间（测试 `test_recorder_refuses_to_write_when_free_space_is_low`、`test_export_checks_available_space`）。

## 8. 资源与运行证据

资源日志列为：

```text
timestamp,uptime_seconds,cpu_percent,rss_mb,disk_write_mb,
system_memory_percent,disk_free_mb,captured,parsed,parse_errors,
queue_dropped,record_dropped
```

- CPU 使用 psutil 进程口径，通常以一个逻辑核满载为 100%，可能超过 100%；报告要注明，不能直接与任务管理器总机器占用混用。
- RSS 是进程驻留内存；`disk_write_mb` 是进程累计写入字节增量，不等同于 pcapng 文件大小。
- 剩余磁盘只被记录，未触发保护；CSV 写入异常也缺少统一的会话故障反馈。
- 会话持续时间使用单调时钟，停止后冻结；开始时间在快照和 JSON 中，GUI 尚未明确展示。
- 时长计数本身不能证明中间始终健康采集，也不能代替休眠、断网和日志缺口检查。

`tools/soak_test.py` 仅运行后台会话，没有 GUI。它具备定时运行、保存和回读汇总，但还没有把提前中断、工作线程退出、时长不足和统计不一致作为严格验收失败条件。正式验证应覆盖 GUI 持续刷新，并保留软件版本、开始/结束时间、连续日志、错误/丢弃计数、抓包样本与截图。
